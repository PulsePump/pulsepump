## Choosing a technology stack

We chose a technology stack by defining critical selection criteria (software requirements) given the project requirements (rapid 3-week turnaround) in an waterfall software development model.

### Weighted selection criteria

| Criteria                         | Description                                                                       | Weight |
| -------------------------------- | --------------------------------------------------------------------------------- | ------ |
| Cross-platform support           | Runs on Windows, macOS, and Linux                                                 | 5      |
| Single codebase                  | Avoids fragmentation across platforms                                             | 5      |
| UI framework maturity            | Breadth and stability of UI components                                            | 4      |
| Scientific (plotting) capability | Quality and performance of visualisation tools and scientific computing functions | 5      |
| Developer familiarity            | Existing team experience with stack                                               | 4      |
| Python/MicroPython compatibility | Enables code reuse with Pico firmware (DRY principle)                             | 5      |
| Development velocity             | Iteration speed, tooling, and DX                                                  | 4      |
| Packaging/deployment             | Ease of distribution and environment management                                   | 3      |

### Candidates

| Stack                     | Strengths                                                                                                                  | Weaknesses                                                                |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Qt / PySide6 / PyQtGraph  | Mature desktop framework; excellent scientific ecosystem integration; high-performance real-time plotting; rapid iteration | Python packaging complexity; higher memory usage                          |
| Electron / React / Plotly | Modern web ecosystem; fast UI development; strong cross-platform distribution                                              | High runtime overhead; weak scientific integration; no MicroPython parity |
| Qt / C++                  | Maximum performance; mature tooling; deep hardware integration                                                             | Slow iteration; high engineering complexity                               |
| Avalonia UI / C#          | Modern cross-platform .NET UX; good desktop tooling                                                                        | Smaller ecosystem; weaker scientific support                              |
| GTK / Python              | Strong Linux integration; Python scientific ecosystem access                                                               | Less polished Windows/macOS UX                                            |
| wxPython                  | Lightweight; native look-and-feel                                                                                          | Smaller ecosystem; dated tooling                                          |
| Web application only      | Highly portable; simple deployment; modern UI patterns                                                                     | Limited hardware access; offline limitations                              |

From the Pugh matrix, we chose Qt/PySide6/PyQtGraph. Investigating its capabilities, we also found that it has a mature panel-based layout engine, which allows for customisable and flexible docking of panels in various positions, and the opening panels as seperate windows. This is perfect for an application like PulsePump, as scientists can tailor the user interface to their specific application, without us having to reinvent the wheel when it comes to window management.

### Choosing developer tooling

#### Package manager

Effective developer tooling helps ship accurate, more maintainable code and enables a fast developer experience for rapid iterative and collaborative development. We chose uv over pip for the Python package manager as it is faster than the standard pip and provides comprehensive project management, helping sync development environments across collaborator machines.

#### Linting, formatting, typechecking

Properly formatted code helps keep code readable, accurate, and conforms to Python standards. Linting helps reduce errors and conform to other stylistic standards. We chose Ruff, which offers linting and formatting in one solution. Typechecking is critical in long-running Python applications to minimise the chance of runtime errors. We chose ty as the language server and typechecker. We wrote tasks in VSCode to automatically run linting, formatting, and typechecking before running the program, halting execution if any errors are found.

## Application implementation

- We began with scripts that flashed the Pico with firmware when the software is built and run, which removes the need to separately use software like Thonny to get firmware onto the microprocessor.
- We wrote basic communication capabilities for the Pico to send sensor data over ther serial port.
- We wrote a basic transformer to convert the 0–3.3 V ADC output to pressure values according to the pressure sensor datasheet.
- We added sampling and pressure sensor panels to the user interface to adjust the sampling rate of the analogue values from the pressure sensors, adjust the pins that the pressure sensors are connected to, adjust the datasheet parameters of the pressure sensor.
- We wrote tasks and run and debug configurations in VSCode to enable debugging and running of standard tasks quickly from the Command Palette.
