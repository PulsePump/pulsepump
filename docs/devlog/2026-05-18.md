# 2026-05-18

The controls system logic will be executed on the Pico, encapsulated in the Pico firmware. This is to:

- reduce the number of serialisation/deserialisations required to execute a control system loop;
- reduce complexity;
- reduce latency;
- allow the Pico to run control loops _independent_ of the desktop client, improving resilience to USB disconnections, running for long periods unattended; and
- improve independent development on the Pico firmware and desktop client.

The resulting pressure profile is a perfect candidate for run length encoding (RLE) as the target pressure profile comprises repeated pulse waves, each block representing one cycle of the heart.

## Programme format

We introduced the [_programme_](../api/core.md) as the top-level artefact representing a target pressure profile. A programme is an ordered sequence of [_blocks_](../api/core.md), where each block stores one cycle of pressure samples and a repeat count. The full waveform is reconstructed by tiling each block's cycle by its repeat count and concatenating the results.

### Compression

The compression is substantial. A typical cardiac experiment at 72 bpm and 100 Hz for 90 minutes requires storing only one cycle of 83 `float32` samples rather than 537,840:

| property               | value     |
| ---------------------- | --------- |
| sampling rate (Hz)     | 100       |
| heart rate (bpm)       | 72        |
| duration (min)         | 90        |
| samples per cycle      | 83        |
| total expanded samples | 537,840   |
| stored samples         | 83        |
| compression ratio      | 6,480 : 1 |

### File format

We chose YAML as the serialisation format. It satisfies the human-readability requirement directly: an engineer debugging an unexpected pressure response can open the file and read the parameters without any tooling. It is also already a project dependency via the openBF model definitions. Binary formats such as MessagePack or HDF5 were considered but rejected because they are not human-readable, which was a stated requirement.

Pressure samples are encoded as `base64` `float32` byte strings within the YAML. This avoids YAML float precision pitfalls of text-serialised floats (e.g. round-trip errors such as `1.3000001`) while remaining embeddable in a plain-text file. `float32` is sufficient for pressure setpoints at typical sensor resolutions and halves the storage cost relative to `float64`.

### Schema and validation

We used `pydantic` v2 to define the schema. The key benefit over plain `dataclasses` is the quality of validation errors: field path, constraint violated, and the received value are all reported together. This is important because programmes will be authored in the UI and exported to files that may be hand-edited or shared between users. Both paths can produce invalid inputs, and clear errors reduce debugging time.

Block sources use a discriminated union on a `kind` field ([`"function_generator"`](../api/core.md) or [`"openbf"`](../api/openbf.md)), which allows `pydantic` to report the exact discriminator mismatch when an unknown source type is encountered.

### Provenance

Each block carries a [`source`](../api/core.md) record alongside its samples. This stores the parameters that generated the samples: the [function generator](../api/core.md) configuration or the [openBF](../api/openbf.md) model key, vessel, and heart rate. Provenance serves three purposes:

1. **Human readability:** the file can be understood without decoding the `base64` samples.
2. **Re-generation:** the UI can reconstruct samples if a parameter is edited.
3. **Auditability:** a saved programme records exactly which model and parameters produced each block, which is important for reproducing experimental conditions.

### Samples are always stored

An alternative design would store only the provenance and regenerate samples lazily on load. This was rejected for [openBF](../api/openbf.md) blocks because the Julia simulation takes tens of seconds and cannot execute on the Pico. Storing samples in the file makes programmes self-contained: they can be transferred, archived, and decompressed without access to the Julia environment or the [openBF models](../api/openbf.md).

### Pico decompression

The desktop client transfers the compressed programme to the Pico over serial. The Pico then calls [`decompress()`](../api/core.md), tiling and concatenating the stored cycles into a flat `float32` array. This produces the raw setpoint buffer the control loop reads from at each tick. Performing decompression on the Pico avoids transferring the full expanded sample array over serial, keeping transfer sizes small. The decompression logic is simple and deterministic, requiring no `YAML` parser, `pydantic`, or openBF toolchain on the firmware.
